# Case 1: open-alert queue per tenant (partial composite index)

Tenant `sql-ev-a`, 200,000 alert rows. Generated by `tools/gen_sql_evidence.py` (re-runnable).

## Query A: queue page (newest 50 open/ack)

Honest result: at 200k rows the planner picks `alert_tenant_opened` (tenant-leading,
`opened_at DESC` order matches the `ORDER BY ... LIMIT 50` so it short-circuits after 78
rows) with or without the partial index — both plans run in ~0.1 ms. The partial index is
not needed for this shape, and we report that instead of cherry-picking.

The partial index still wins on footprint: `alert_open_queue` is **1040 kB vs 15 MB** for
the full-tenant index (only open/ack rows indexed), i.e. less write amplification and less
cache pressure on the alert write path.

## Query B: open-alert count (dashboard badge)

`SELECT count(*) FROM alert WHERE tenant_id = :t AND status = 'open'` (100,303 matching rows).

```
        Workers Planned: 2
        Workers Launched: 2

```

### AFTER (`CREATE INDEX alert_open_queue ... WHERE status IN ('open','ack')`): index-only scan, 93 buffers, ~10.7 ms

```
Aggregate  (cost=2359.38..2359.39 rows=1 width=8) (actual time=10.656..10.657 rows=1 loops=1)
  Buffers: shared hit=93
  ->  Index Only Scan using alert_open_queue on alert  (cost=0.42..2108.64 rows=100296 width=0) (actual time=0.070..6.707 rows=100303 loops=1)
        Index Cond: ((tenant_id = 'bb312e09-003a-4f78-acbb-1eea4d2ac3ac'::uuid) AND (status = 'open'::text))
        Heap Fetches: 0
        Buffers: shared hit=93
```

37x fewer buffer hits, no parallel workers needed, zero heap fetches (visibility map hot).
Lesson for the write-up: the partial index pays for counting/filtering shapes, not for
order-by-limit shapes — which is exactly why both indexes coexist in `0006_perf.sql`.
